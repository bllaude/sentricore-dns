Security at Sentricore

A resolver sees every domain your network asks about. That makes privacy and hardening first-class product requirements, not afterthoughts.

Design principles

  • Local-first. Query history lives in your SQLite file. There is no phone-home, no accounts, no cloud dependency to breach.
  • Secure by default. Blocklist write APIs refuse requests unless an API key is configured; with no key set, writes are denied outright.
  • Small surface. The proxy speaks UDP on one port; the dashboard binds 127.0.0.1 unless you deliberately expose it behind a reverse proxy.
  • Defense in depth. Per-client token-bucket rate limiting contains noisy or compromised hosts before they can amplify traffic upstream.

Hardening checklist

# 1. Set a strong API key (long random string) for the web service
export SENTRICORE_API_KEY="$(openssl rand -hex 32)"

# 2. Keep the dashboard loopback-only and front it with TLS via nginx/caddy
# 3. Run containers as non-root and pin image digests
# 4. Restrict who may reach :5300 with your firewall
sudo ufw allow from 192.168.0.0/24 to any port 5300 proto udp
# 5. Back up (or rotate) data/sentricore.db if query history is sensitive

Known limitations (stated honestly)

  • DNS traffic between client and proxy is UDP and unencrypted by default — encrypt the last hop with DNS-over-TLS at the client or a tunnel if that matters in your threat model.
  • Blocking is domain-exact; IP-based exfiltration and DoH bypass require complementary egress controls.
  • SQLite is single-node by design; large fleets should ship logs to a central store themselves.

Responsible disclosure

Found a vulnerability? Email security@sentricore.dev with private details. We acknowledge reports within 3 business days and aim to ship fixes within 30 days for confirmed issues. Please avoid public issue trackers until a patch exists.
